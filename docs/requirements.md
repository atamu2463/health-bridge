# HealthBridge 要件定義

## 1. 文書の位置づけ

本書では、MVPの要件と、現在のモックUIで確認できる範囲を分けて記載します。

- 参照資料：Googleドキュメント「【Docs】体調管理・共有アプリ」の「要件定義・技術選定 v2（再レビュー用）」「画面設計 v2（再レビュー用）」「DB設計v2」「API設計v2」「2026.09.17MTG」
- 資料参照日：2026年9月18日
- 画面例：ローカルの最新版を起動し、モックデータの描画完了後に撮影

v2資料にはレビュー前の案も残っているため、第2回レビュー後の決定、Issue #110 / #112 / #133、現在のコードと照合しています。

## 2. 開発背景・解決したい課題

### 従業員側

体調を定期的に記録・可視化し、本人が変化を振り返ることで、セルフケアや必要な配慮・サポートの相談につなげやすくすることを目指します。

### 管理者側

担当従業員の体調記録を一覧・履歴から確認し、注意が必要な従業員や未入力の従業員を把握しやすくすることで、声かけや配慮を検討するための情報を提供します。

## 3. 対象ユーザー

初期運用は従業員10名程度の小規模組織を想定し、employee（従業員）とmanager（管理者）の2種類を対象とします。大規模組織向けの上位権限、部署・役職情報は将来検討です。

## 5. 主な業務ルール

> 本節は現行MVPの業務ルールを示します。5.1のcondition・timingコードと5.3、5.4の担当関係・ID表現はIssue #124、5.5、5.6の認証・認可とAPI共通仕様はIssue #133で、実装前の設計として確定しました。いずれも現時点では未実装です。

### 5.1 体調記録

- 体調は次の5段階とし、「普通」をグラフ中央に置く

| conditionコード | 画面表示 | score |
| --- | --- | ---: |
| `excellent` | とても良好 | 2 |
| `good` | 良好 | 1 |
| `normal` | 普通 | 0 |
| `caution` | 注意 | -1 |
| `bad` | 悪化 | -2 |

- 1日につき出勤時・退勤時の2回を別レコードとして記録し、APIのtimingにはそれぞれ `clockIn`、`clockOut` を使用する
- DBのテーブル名・カラム名などの識別子はsnake_caseとするが、`health_records.timing` に保存するコード値はAPIと同じ `clockIn`、`clockOut` とする
- コメントを必須とする
- 同一employee・同一日・同一timingは1件だけとし、初期MVPでは入力後の上書きを行わない
- employeeは本人の体調だけを入力し、managerによる代理入力は行わない

### 5.2 未入力

- 未入力は体調状態として保存せず、対象レコードの不存在から判断する
- 一覧の「未入力」は、指定日の出勤時記録が存在しないemployeeを対象とする
- 出勤時が未入力でも退勤時は入力でき、退勤時だけが未入力の場合は一覧の「未入力」絞り込み対象にしない
- グラフは欠測値そのものを描画せず、前後に記録がある欠測区間だけ点線で結ぶ

### 5.3 担当関係・アカウント

- 1人のemployeeへ現在の担当managerを1人設定する
- DBでは `users.manager_id` によって担当managerと関連付け、氏名文字列だけを関連付けに使用しない
- managerは自身の担当employeeだけを参照・更新できる設計とし、API側でも検証する
- API-13の引き継ぎ先は、DB上で `role = manager` かつ `is_active = true` のユーザーに限定し、API側で検証する
- 担当変更後は旧managerから対象employeeを参照・更新できない
- employee作成時は、作成したmanagerを初期担当者とする
- 担当変更後もemployeeアカウントと過去の体調記録を保持する
- employeeの利用停止は物理削除せず無効化し、通常の一覧から除外して過去の記録を保持する
- メールアドレスはユーザー間で重複させない
- managerの表示が必要なAPIレスポンスでは、少なくとも文字列の `id` と `name` を持つオブジェクトを返す
- クライアントから送信されたroleやmanager IDを認可判断に使用せず、認証済みユーザーとDB上の担当関係をAPI側で検証する

managerの表示例：

```json
{
  "id": "1",
  "name": "鈴木 花子"
}
```

### 5.4 IDとAPI境界

- PostgreSQLの各テーブルの主キーは整数とする
- APIのリクエスト・レスポンスではIDを文字列として表現し、フロントエンドの既存の `string` 型を維持できるようにする
- パスパラメータも文字列として受け取り、バックエンドで妥当な整数IDへ変換・検証してからDB処理に使用する
- モック固有の `new-...` 形式の仮IDは、実API接続後には使用しない
- モックで固定しているユーザーID `"1"` は本番設計へ採用せず、認証済みユーザーのIDをサーバー側で特定する

### 5.5 認証・セッション（設計済み・未実装）

- JWTは使用せず、PostgreSQLで管理するサーバー側セッション方式とする
- パスワードはbcryptでハッシュ化し、平文では保存しない。bcryptはパスワードに使用し、セッショントークンには使用しない
- ログイン時は `crypto/rand` で32バイトのランダム値を生成し、Base64 URL形式にエンコードしたセッショントークンをCookieへ格納する
- DBにはセッショントークンそのものではなくSHA-256ダイジェストを保存する
- 認証時はCookieのトークンから同じSHA-256ダイジェストを生成し、対象セッションを検索する
- セッション有効期限は24時間とし、ログアウト時は対象セッションを削除してCookieを失効させる
- Cookie名は `health_bridge_session` とし、JavaScriptから読み取れないよう `HttpOnly`、`Path=/api` を設定する
- Cookieの発行と失効には同じCookie名と `Path=/api` を使用する
- 本番環境は `Secure=true`、`SameSite=None` とし、ローカル環境はHTTPで検証できる設定へ切り替える
- managerはMVPでは管理用CLIで作成する。一般登録、組織用招待コード、メール認証はMVP対象外とする
- 現在のmanager登録画面はモックUIとして残すが、実APIへは接続しない

### 5.6 APIの認証・認可と共通ルール（設計済み・未実装）

- フロントエンドはCookieを送信するリクエストで `credentials: "include"` を使用する
- credential付きCORSではワイルドカードOriginを使用せず、環境変数で許可したOriginだけを応答に設定する
- クロスオリジンの状態変更リクエストで発生する `OPTIONS` preflightへ応答し、`Access-Control-Allow-Methods` に `GET`、`POST`、`PUT`、`PATCH`、`DELETE`、`OPTIONS` を設定する
- JSONリクエストでは `Content-Type: application/json` を使用し、`Access-Control-Allow-Headers` に `Content-Type` を設定する
- 将来ほかの非単純ヘッダーを使用する場合は、`Access-Control-Allow-Headers` へ対象ヘッダーを明示的に追加する
- CSRF対策として、`POST`、`PUT`、`PATCH`、`DELETE` の状態変更リクエストでは `Origin` が許可Originと一致することをAPI側で検証し、GETではデータを変更しない
- 未認証、無効または期限切れのセッションは `401 Unauthorized`、認証済みで権限がない場合は `403 Forbidden` とする
- 認証時にユーザーの有効状態を確認し、無効化済みユーザーは既存セッションが残っていても認証を許可せず `401 Unauthorized` とする
- 無効化済みユーザーに紐づくセッション行を削除するタイミングは実装時に決定する
- role、本人のユーザーID、担当managerはセッションとDBから特定し、クライアントが送信した値を認可根拠として信用しない
- employeeは本人の情報と体調記録だけを操作できる
- managerは現在担当しているemployeeだけを参照・操作でき、担当変更後の旧managerには許可しない
- 業務上の日付境界は `Asia/Tokyo` とする
- APIエラーは原則として `error.code` と利用者向けの `error.message` を持つ共通形式で返し、利用者向けレスポンスには内部エラーの詳細を含めない
- サーバーログには調査に必要な情報を残すが、パスワード、セッショントークン、DB接続情報などの秘密情報は出力しない

```json
{
  "error": {
    "code": "invalid_request",
    "message": "リクエスト内容を確認してください"
  }
}
```

## 6. 現在の完成範囲とMVP後の候補

### 6.1 現在の完成範囲

- フロントエンド：モックUIと主要操作フロー
- バックエンド：Go / Gin / GORMのPostgreSQL接続、`GET /health`、JSONエラー、CORS、graceful shutdownの共通基盤、4テーブルのモデル／マイグレーション、マスターデータ
- 未完成：実認証、サーバー側認可、業務API、業務データのAPI経由での永続化、フロントエンドAPI接続、バックエンド公開

### 6.2 MVP後・将来検討

- チーム全体の体調変化の傾向を分析
- 年間等の長期間グラフ
- 未入力メール通知
- 体調記録の修正
- 担当manager変更履歴
- 無効化アカウントの保持期間と自動削除
- managerの一般登録、組織用招待コード、メール認証
- パスワード再設定
- 大規模組織向けの上位権限、部署・役職情報
- 従業員数増加時の一覧検索
- 同じ体調が続く場合の支援方法や、改善要因を把握する運用
