# HealthBridge システム構成

## 1. 概要

HealthBridgeは、Next.jsで構築したフロントエンド、Goで構築するバックエンドAPI、PostgreSQLデータベースから構成するWebアプリケーションです。

開発環境ではDocker Composeを使用し、フロントエンド・バックエンド・PostgreSQLをそれぞれ独立したコンテナとして構成します。

現在はフロントエンドの画面プロトタイプと、Go / GORMからPostgreSQLへ接続するためのバックエンド基盤、HTTPサーバー、Health Check APIまで実装しています。業務API、認証・認可、DBモデル・マイグレーションについては、第2回スタッフレビューでMVP仕様を確認した後に実装する予定です。

## 3. 各コンポーネントの役割

### 3.1 フロントエンド

フロントエンドは、従業員・管理者がHealthBridgeを操作するための画面を担当します。

主な役割は以下のとおりです。

- 従業員・管理者向け画面の表示
- 体調記録入力フォームの表示
- 体調履歴・グラフの表示
- 担当従業員一覧・絞り込み画面の表示
- 従業員アカウント管理画面の表示
- ユーザー操作に応じたバックエンドAPIへのリクエスト

主要技術として、Next.js、React、TypeScript、Tailwind CSS、Rechartsを使用しています。

現在は主要画面と操作フローをモックデータで確認できるプロトタイプを実装しています。

### 3.2 バックエンド

バックエンドは、フロントエンドからのリクエストを受け取り、業務ルールに基づいた処理とデータベース操作を担当します。

主な役割は以下を想定しています。

- ユーザー認証・認可
- 管理者・従業員アカウントの管理
- 体調記録の登録・取得
- 担当従業員の取得・絞り込み
- ユーザーの役割・担当関係に基づくアクセス制御
- PostgreSQLへのデータ保存・取得

バックエンドにはGoを使用し、PostgreSQLとの接続にはGORMを使用します。

現時点ではGo / GORMからPostgreSQLへ接続する処理、HTTPサーバー、Health Check API（`GET /health`）まで実装しており、業務APIは未実装です。

### 3.3 データベース

データベースにはPostgreSQLを使用します。

現在のDB設計では、主に以下の4テーブルを使用する予定です。

| テーブル | 役割 |
| --- | --- |
| `users` | 管理者・従業員のアカウント情報と担当管理者を管理する |
| `health_records` | 従業員の出勤時・退勤時の体調記録を管理する |
| `roles` | `manager`・`employee`のロールを管理する |
| `conditions` | 5段階の体調状態を管理する |

`users.manager_id`によって、従業員と現在の担当管理者の関係を表現します。

体調記録は`health_records`へ保存し、同一従業員・同一日・同一記録タイミングにつき1件となるようにします。

「未入力」は体調状態としてデータベースへ保存せず、対象となる体調記録が存在しないことから判定します。

担当管理者の変更やチーム全体の体調傾向についても、既存のテーブルを利用して実現し、現時点では専用テーブルを追加しない方針です。

## 4. 現在の実装状況

設計と実装の進捗は以下のとおりです。

| 項目 | 状況 | 現在の内容 |
| --- | --- | --- |
| フロントエンド | 実装済み | 主要画面・操作フローをモックデータで確認可能 |
| Docker Compose | 構築済み | Frontend / Backend / PostgreSQLの開発環境を構成 |
| PostgreSQL | 接続処理実装済み | Go / GORMから接続する処理を実装 |
| HTTPサーバー | 実装済み | GoのHTTPサーバーを実装 |
| Health Check API | 実装済み | `GET /health`でHTTPプロセスの稼働状態を確認可能 |
| DBモデル | 設計済み・未実装 | `users` / `health_records` / `roles` / `conditions`を設計 |
| マイグレーション | 未実装 | MVP仕様確定後にGORMで実装予定 |
| 業務API | 設計済み・未実装 | 体調記録・従業員管理などのAPIを設計 |
| 認証・認可 | 設計済み・未実装 | manager / employeeの役割と担当関係に基づく制御を予定 |
| Frontend / API接続 | 未実装 | 現在のフロントエンドではモックデータを使用 |
| CI | 未実装 | バックエンドのテスト整備後にGitHub Actionsを導入予定 |

設計済みの項目についても、スタッフレビューによってMVP仕様が変更された場合は、設計を修正してから実装へ反映します。

## 5. 今後の実装方針

第2回スタッフレビューでMVP仕様を確認した後、以下の順序でバックエンド実装を進めます。

1. レビュー結果を要件・DB・API設計へ反映する
2. GORMによるDBモデル・マイグレーションを実装する
3. 体調記録など、主要な業務APIを実装する
4. 認証・認可とアクセス制御を実装する
5. フロントエンドをバックエンドAPIへ接続する
6. テストとGitHub ActionsによるCIを整備する

実装では、画面単位で必要な機能をまとめて実装・確認し、フロントエンドからデータベースまで一連の処理が動作する状態を段階的に増やしていく方針です。
