# HealthBridge

従業員が日々の体調を記録し、本人の振り返りと管理者による状況把握を支援する体調管理・共有アプリです。

現在は、就労移行支援事業所のスタッフによる第2回レビュー後のMVPを、フロントエンドのモックUIで確認できる段階です。Go / Gin / GORMによるバックエンド共通基盤をRenderへ、PostgreSQLをSupabaseへ公開していますが、認証・認可・業務API・フロントエンドとの接続は未実装です。

## 公開環境

- フロントエンド（Vercel）：https://health-bridge-management.vercel.app/
- バックエンド（Render）：https://health-bridge-p3kx.onrender.com
- バックエンドのヘルスチェック：https://health-bridge-p3kx.onrender.com/health

バックエンドのルート `/` は実装していないため、バックエンドURLを直接開くと404を返します。稼働確認にはヘルスチェックURLを使用します。また、Render Freeプランのスリープ後は、初回アクセスに時間がかかる場合があります。

> [!IMPORTANT]
> 公開デモは画面・操作フローを確認するためのモックUIです。入力内容はブラウザ内の一時状態としてのみ扱われ、実認証、サーバー側の認可、業務API、DB永続化は動作しません。
>
> 2026年9月19日に、企業提出版MVPが公開デモへ反映されていることを確認しました。

### コードで確認したデモ操作

ログイン画面では、入力形式を満たして送信すると利用者別メニューへ進みます。ただし、資格情報の照合は行っていません。

- 従業員：体調入力、1週間／1か月の履歴・グラフ表示、出勤時／退勤時系列の表示切替
- 管理者：日付別の担当従業員一覧、「注意」「悪化」「未入力」の絞り込み、個人詳細、従業員作成・編集・無効化、担当管理者変更
- 共通：利用者別メニューとログアウト導線

操作後のデータはモック状態でのみ更新され、再読み込み時には初期状態へ戻ります。詳細な実装状態と全画面例は[要件定義](docs/requirements.md)に記録しています。

## 開発背景

就労移行支援事業所へ通い始めて、自分と同じように心身の特性の影響で安定して働けない方々がたくさんいることを知りました。\
一方、セルフケアができたうえで適切なサポートを受けられれば安定して働ける人が増えるだろうと考えました。\
社員の体調の変化にいちはやく気づき、お互いにサポートし合える仕組みがあればよいのではと思い、本アプリの開発を始めました。

## 解決したい課題

### 従業員

日々の体調を記録・可視化することで、自分の体調変化を振り返りやすくし、セルフケアや必要な配慮・サポートの相談につなげることを目指しています。

### 管理者

担当する従業員の体調や変化を把握しやすくすることで、必要な声かけや配慮を検討するための情報として活用できることを目指しています。

## 対象ユーザー

初期運用は、従業員10名程度の小規模チームを想定しています。

- 従業員：出勤時・退勤時の記録と、自身の履歴・グラフの振り返り
- 管理者：担当従業員の状況確認と、従業員アカウント・担当関係の管理

## 主な機能

※主要な機能のみ掲載します。詳細は[要件定義](docs/requirements.md)ドキュメントをご確認ください。

### 従業員機能

#### 体調入力機能

従業員は、出勤時・退勤時に体調とその要因を入力します。同じ日・同じタイミングでの体調記録更新はできない仕様になっています。

![体調入力画面](docs/images/04-health-input.png)

#### 体調グラフ機能

1週間／1か月単位・および出勤時と退勤時の体調の変化を折れ線グラフで確認できます。体調の変化を可視化することで、体調悪化の予防策を実行したり、体調改善の要因を分析したりできます。

![体調グラフ機能](docs/screenshots/issue112/01-pc-month-both.png)

### 管理者機能

#### 担当従業員の状況を確認

日付を指定して、自分が管理する従業員の出勤時・退勤時の体調とコメントを一覧で確認できます。「注意」「悪化」「未入力」従業員の絞り込み表示もできます。

![担当従業員確認画面](docs/images/10-manager-dashboard.png)

#### 担当従業員の体調グラフを確認

従業員個人の体調グラフや入力履歴を確認できます。体調データを従業員と管理者で共有して、安定就労のための対策を検討・実行しやすくすることを目的とした機能です。

![担当従業員詳細画面](docs/images/11-manager-employee-detail.png)


### MVP対象外・将来拡張（案）

## 技術選定理由

### 画面プロトタイプ（v0）

画面設計にかける時間を抑え、要件整理や実装に時間を使うため、v0を活用しました。\
生成後は、スタッフレビューをもとに表示・操作・レスポンシブ対応を修正しています。

### フロントエンド（TypeScript / Next.js）

TypeScriptは、型チェックによってデータの受け渡しや処理の誤りに気づきやすくするために採用しました。

Next.jsは、今回v0が生成したコードの構成を引き継いで使用しています。\
今回のアプリ規模であればReact＋Viteでも実現できますが、構成の変更よりも機能実装とレビュー後の改善を優先しました。

### バックエンド（Go / Gin）

Goは、新卒研修で使用した経験があり、既存知識を活かして実装を進めたいと考え、採用しました。
HTTPルーティングとmiddlewareにはGinを使用し、ルーターを起動処理から分離してテストしやすい構成にしています。

## ローカル開発環境

DockerとDocker Composeを使用して、フロントエンド、バックエンド、PostgreSQLを起動できます。

### 1. 環境変数の準備

```bash
cp .default.env .env
```

`.env`へ、ローカル開発用のPostgreSQL設定を入力してください。

```env
POSTGRES_USER=任意のユーザー名
POSTGRES_PASSWORD=任意のパスワード
POSTGRES_DB=health_bridge
BACKEND_PORT=8080
ALLOWED_ORIGINS=http://localhost:3000
```

実際の認証情報や本番環境の値はコミットしないでください。

### 2. 起動

```bash
docker compose up -d --build
```

バックエンドのコードを変更した場合も、イメージを更新するため`--build`を付けて起動します。

### 3. マイグレーション

```bash
docker compose exec backend /usr/local/bin/migrate
```

起動済みの`backend`コンテナ内でマイグレーションを実行します。

`roles`、`users`、`conditions`、`health_records`を作成し、`roles`と`conditions`のマスターデータを投入します。複数回実行してもテーブルやマスターデータは重複しません。デモユーザーやデモ体調記録は投入しません。

### 4. バックエンドの起動確認

```bash
curl http://localhost:8080/health
```

次のJSONが返れば、バックエンドのHTTPサーバーは起動しています。

```json
{"status":"ok"}
```

このエンドポイントはHTTPプロセスの稼働確認用であり、PostgreSQLへの疎通確認は行いません。

### 5. 停止

```bash
docker compose down
```

PostgreSQLのデータはDockerボリュームに保持されます。通常の停止では`docker compose down -v`を使用しません。
